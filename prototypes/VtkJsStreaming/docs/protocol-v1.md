# PrePoMax render protocol 1.0

This document is the implementation companion to sections 9–12 of the specification. The normative source remains `VTKJS_STREAMING_RENDERER_SPEC.md` until this document reaches parity.

## Identity and versions

Scene, actor, chunk, resource, and message IDs are canonical lowercase UUID strings. Source node and element IDs are signed 32-bit integers. Local connectivity is unsigned 32-bit. A scene snapshot carries `sceneRevision`; actors separately carry topology and field versions.

All API responses include `X-PrePoMax-Protocol: 1.0`. A non-1.x requested header or non-1.0 command envelope receives HTTP 426 and `protocol-version-unsupported`.

## Endpoints

| GET | `/api/v1/scenes/{sceneId}/manifest` | consistent JSON snapshot |
| GET | `/api/v1/scenes/{sceneId}/resources/{resourceId}` | raw binary array |
| POST | `/api/v1/scenes/{sceneId}/section` | transient server-derived section geometry |
| GET | `/api/v1/scenes/{sceneId}/events` | WebSocket upgrade |
| POST | `/api/v1/scenes/{sceneId}/commands` | JSON control fallback |

| POST | `/api/v1/host/shutdown` | credentialed graceful host shutdown |
| POST | `/api/v1/host/actors/visibility` | bounded host actor visibility update |
| POST | `/api/v1/host/camera/{view}` | standard camera/reset update |
| POST | `/api/v1/host/camera/custom` | absolute Float64 camera update |
| POST | `/api/v1/host/actor` | actor rename/color update |

All `/api` routes other than session creation require the session cookie, `X-PrePoMax-Session`, or bearer credential. Browser WebSockets authenticate with the same-origin HttpOnly cookie.

An accepted `actor.visibility.updated` batch mutates existing browser actors without fetching resources, then adjusts camera depth and clipping from the remaining visible bounds while preserving parallel scale and emits `prepomax.camera.changed-v1`. If the batch hides every actor, the last valid camera is retained and reported unchanged. `actor.removed` applies the same bounds policy after disposing the removed pipelines and overlays.

Sessions expire and the server keeps a configured hard maximum. Exhausted capacity returns retryable HTTP 503 with `session-capacity-reached`. Commands use an independent per-session fixed window; exhaustion returns retryable HTTP 429 with `command-rate-limited` and `Retry-After`. Unsupported command types return HTTP 400 with `command-unsupported` and are never acknowledged as completed.

## Binary arrays

The descriptor supplies semantic, `dataType`, components, element count, byte length, byte order, encoding, SHA-256, version, immutability, and URI. Bodies have no header or padding. V1 data is little-endian and identity encoded with content type `application/vnd.prepomax.render-array`.

Triangle connectivity is `[p0,p1,p2,...]` in chunk-local indices. The client converts it once to VTK packed cells `[3,p0,p1,p2,...]`. Source-element IDs contain one signed ID per rendered triangle; source-point IDs contain one signed ID per local point.

Immutable resources return a hash ETag, `Cache-Control: private, immutable`, and byte-range support. Development clients verify SHA-256 after checking byte length and before constructing a typed view.

## Coordinates, fields, and future deformation

`worldOrigin` is float64 JSON metadata. Position resources are float32 offsets. CPU pick coordinates are reconstructed with JavaScript numbers as `worldOrigin + relativePosition`.

Point fields are float32 with one value per local point. NaN means unavailable and infinity is invalid. A field update publishes a new scalar descriptor without changing position or connectivity IDs.

`field.toggle` is the deterministic WP3 command. It must carry the last observed scene revision. A successful command increments the scene revision and publishes `field.updated` with field metadata plus one `{ actorId, chunkId, fieldVersion, resource }` entry per affected chunk. Each resource descriptor has semantic `pointScalars`; topology/source-ID descriptors are forbidden in this payload. The client downloads every replacement first, then updates existing scalar arrays as one activation step. A stale command returns `revision-conflict` and does not publish an event.

## Embedded camera interaction

The exact-origin host arms one-shot box zoom with `{ "type": "prepomax.box-zoom.mode-v1", "enabled": true }`. While armed, an unmodified primary-pointer drag takes precedence over area selection and displays the existing rectangle overlay. A valid rectangle pans its world-space center to the viewport center, divides orthographic parallel scale by the limiting viewport-to-rectangle ratio, resets clipping, renders, and publishes the normal bounded `prepomax.camera.changed-v1` snapshot. Escape, pointer cancellation, or an undersized rectangle does not mutate the camera. Both outcomes disarm locally and emit `{ "type": "prepomax.box-zoom.ended-v1", "applied": boolean }`, allowing the host to clear its toolbar state. The host ignores completion when no box-zoom mode is active.

The host configures follower motion with `{ "type": "prepomax.follower-view.updated-v1", "actorNames": string[], "nodeIds": integer[] }`. Both arrays must have the same length, which is restricted to zero (disabled), one (point follower), or three (plane follower); names are bounded to 1,024 characters. The client retains valid state across scene-view recreation and captures a world-coordinate baseline only after all named source nodes can be resolved from loaded chunk `sourcePointIds`. A point follower removes motion along the current view-plane normal and translates camera position/focal point by the remaining delta. A plane follower reproduces the legacy centroid/basis transform and rotates view-up. Frame activation reports `followerAdjusted`; `cameraAdjusted` independently reports the subsequent visible-bounds depth/clipping adjustment.

Before `scene.replaced` destroys a loaded view, the client snapshots the currently resolved follower points in world coordinates. It gives that baseline to the replacement view before loading, which makes the comparison independent of a changed floating origin. After snapshot loading, it applies the replacement event's retained camera, evaluates the follower transform, adjusts depth/clipping once when a transform was applied, waits for stable paint, and sends `{ "type": "prepomax.follower-view.applied-v1", "sceneRevision": integer, "followerAdjusted": boolean, "cameraAdjusted": boolean }`. The exact-origin host accepts the completion only while a follower definition is active.

## Exploded-view preview

The exact-origin host sends transient actor translations as `{ "type": "prepomax.exploded-view.preview-v1", "offsets": [{ "actorName": string, "offset": [number, number, number] }], "animate": boolean, "durationMs": integer, "requestId"?: string }`. A message contains at most 512 unique, non-empty actor names of at most 1,024 characters. Every vector component must be finite with absolute value at most `1e150`; duration is bounded to 0 through 60,000 ms. An optional request ID is exactly 32 hexadecimal characters. A zero vector removes the retained translation for that actor but remains part of the explicit update batch. Navigation recovery republishes retained nonzero state without a request ID.

The client translates every chunk for the named actor and its selection-overlay actors. Animated updates interpolate from each current translation with the legacy arctangent easing curve and adjust camera depth/clipping at every rendered step. A newer update cancels an older animation. On completion the client emits `{ "type": "prepomax.exploded-view.applied-v1", "actorCount": integer, "animated": boolean, "requestId"?: string }`; the host repeats the count and ID validation and advances a pending commit only for the exact request. If acknowledgement is unavailable, the host advances through a bounded `durationMs + 2,000` ms fallback.

The preview does not mutate server resources or source identities. Point-pick candidate bounds include the translation, while the visual hit is inverse-translated before `pick.resolve`; selection precision remains based on the visual hit. Follower source-node positions include the translation. Rectangle selection is unavailable while any nonzero preview exists because the server locator has no per-actor transform state. A complete `scene.replaced` clears preview state before loading the replacement because committed exploded geometry already contains the displacement. After loading that snapshot, applying its retained camera and follower transform, and waiting for stable paint, the embedded client emits `{ "type": "prepomax.scene.applied-v1", "sceneRevision": integer }`. The controller retains its transition guard until that exact-origin completion or a 15-second fallback.

For activation, the preview target is the computed positive part offset and the controller mutates the mesh only after `exploded-view.applied`; the baked replacement then clears the transient offset. For deactivation, the current scene is already baked, so the preview target is the negative stored offset; only after the terminal frame does the controller restore the base mesh. This ordering keeps the final preview frame and first replacement frame visually equivalent in both directions.

## Section-view surface clipping

The exact-origin host owns one retained section state: `{ "type": "prepomax.section-view.updated-v1", "enabled": boolean, "point": [number, number, number], "normal": [number, number, number], "lightenColors": boolean, "sectionColor": [number, number, number, number] }`. Point and normal components must be finite with absolute value at most `1e150`; the normal must be nonzero and is normalized by both host and client. Color components are finite and restricted to 0 through 1. The point is in absolute model coordinates. A disabled message still contains valid canonical point, normal, and color values.

The client subtracts the current scene `worldOrigin`, creates one `vtkPlane`, and attaches it to every streamed chunk mapper and every selection-overlay mapper. Updates mutate that plane without replacing base pipelines. New chunks and overlays inherit the retained plane. Navigation and `scene.replaced` recreate it after the new floating origin is known. Removal detaches and deletes the plane. Completion is `{ "type": "prepomax.section-view.applied-v1", "enabled": boolean, "clippedChunks": integer, "capActors": integer, "skippedCells": integer }`, bounded to 512 chunks/actors and 5,000,000 skipped cells.

For each enabled state, the browser cancels any older request and posts the absolute plane, presentation policy, and current per-actor exploded offsets to the authenticated section endpoint. The server intersects retained full cells, never visible surface triangles. Linear tetrahedra, voxels, hexahedra, wedges, and pyramids produce triangulated cut polygons plus element-border lines; line/triangle/quad shell cells produce cut lines. VTK type 24 quadratic tetrahedra follow the exact VTK 5.8 `vtkQuadraticTetra::Contour` topology: eight fixed linear tetrahedra are contoured with the legacy marching-tetra case table. Types 25 and 29 follow the corresponding eight-linear-hexahedron decomposition and exact 256-case VTK 5.8 marching-cubes edge table. Type 25 synthesizes the six face centers and one cell center with the legacy twenty-node interpolation weights; type 29 consumes its supplied 27 nodes. Type 26 synthesizes three rectangular-face centers with the legacy fifteen-node interpolation weights, subdivides into eight linear wedges, and uses the exact 64-case VTK 5.8 wedge table. Type 27 synthesizes its quadratic base-face center with the legacy thirteen-node interpolation weights, contours six linear pyramids with the exact 32-case pyramid table, and contours four internal linear tetrahedra with the marching-tetra table. Generated type-25, type-26, and type-27 face identities are shared by adjacent cells, and cap-border lines are derived from triangle incidence so internal subdivision edges are suppressed. These paths retain internal subdivision vertices, scalar interpolation, and per-triangle element identity. Subdivision is gated by a nondegenerate outer-edge crossing so uncut large-model cells do not pay the subcell cost. Shared intersections are deduplicated, winding follows the normalized plane, and host scalar/frame updates refresh retained locator scalars.

The response content type is `application/vnd.prepomax.section-geometry-v1`. Its little-endian `PMXSEC1\0` body starts with actor and skipped-cell Int32 counts. Each non-pickable actor carries length-prefixed actor/parent/name strings, four Float32 color components, Float32 line width, point/triangle/line counts, six Float64 world bounds, origin-relative Float32 positions, UInt32 triangle and line connectivity, Float32 point scalars, and one Int32 source element ID per triangle. Server and decoder independently enforce 512 actors, 500,000 points, 500,000 triangles, exact lengths, finite coordinates/colors/bounds, non-infinite scalars, and in-range connectivity. Requests do not advance scene revision or retain per-plane resources. Replacement atomically disposes the prior cap pipelines; disable removes them. Exploded previews are included in plane resolution and applied as the same actor translation in VTK.js.

Hardware point picking sees only displayed clipped fragments, while the existing `pick.resolve` continues to validate the immutable source triangle. Generated section geometry is non-pickable. Rectangle selection remains enabled. Both selection requests carry the same optional absolute `sectionPlane: { point, normal }`; the retained side follows vtk.js exactly, `dot(normal, worldPoint - point) >= 0`. The server normalizes and validates the plane independently, so an invalid or zero normal cannot bypass clipping.

## Pick resolution

`pick.resolve` carries the current scene revision and a visual candidate with `actorId`, `chunkId`, `renderPrimitive: "triangle"`, `primitiveIndex`, `sourceElementId`, `candidateSourceNodeId`, three-component `worldPosition`, two-component canvas `displayPosition`, three-component `cameraDirection`, positive `selectionPrecision`, and `mode: "element"`. The browser derives `selectionPrecision` as the world-space distance represented by seven CSS pixels at the validated hit depth, matching the legacy geometry-pick threshold. It does not change the scene revision.

The service validates the candidate against its own immutable topology and current actor state. Selection precision must be finite, positive, and bounded relative to the current scene span. A success is `command.completed` with `payload.commandType: "pick.resolve"` and `payload.result`, including `validated: true` and the three server-derived `triangleSourceNodeIds`. The browser never supplies those authoritative triangle-node IDs. A malformed or inconsistent candidate returns HTTP 400 with stable code `pick-invalid`; a stale revision still returns `revision-conflict`.

In the embedded client only, a successful response is forwarded to WebView2 as a JSON string with `type: "prepomax.pick.validated-v1"`, `validated: true`, actor name, source element/node IDs, selection precision, and operation `replace`, `add`, `subtract`, or `intersect`. The host accepts this envelope only from the exact renderer scheme/host/port. Operations preserve the legacy modifier mapping: no modifier replaces, Shift adds, Ctrl subtracts, and Shift+Ctrl intersects. PrePoMax revalidates the chosen ID against its displayed mesh before updating node, element, part, surface, geometry-vertex, geometry-edge, geometry-surface, or mixed-geometry selection state.

PrePoMax sends its authoritative selection back through WebView2 as `prepomax.selection.updated-v1`, with `item` set to `none`, `node`, `element`, `surface`, `geometry-edge`, `geometry`, `part`, or `unsupported`, plus integer `ids`, exact actor names, exact per-face source-node definitions in `faceNodeIds`, and two- or three-node model-edge cells in `edgeNodeIds`. The JSON path remains limited to 100,000 IDs, 100,000 faces, one million face-node references, 100,000 edge cells, 300,000 edge-node references, and 4,096 actor names. The client retains the last valid message across scene-view recreation. Element IDs produce orange triangle outlines, surface definitions outline only triangles whose three source nodes belong to the same selected face, geometry-edge cells produce orange lines with quadratic cells ordered start-mid-end, node IDs produce orange point markers, and part names produce orange wireframe overlays without changing the underlying pickable actors. `geometry` composes the face, edge, and vertex overlay paths in one authoritative state.

Selections above a JSON bound use a read-only WebView2 shared buffer with the little-endian `PMXSEL1` signature and `prepomax.selection.shared-v1` metadata. Its 40-byte header carries version, item code, and declared ID/name/face-reference/edge-reference counts, followed by Int32 IDs, length-prefixed strict UTF-8 actor names, and length-prefixed Int32 face and edge cells. Both sides enforce a 64 MiB envelope, at most 8,000,000 IDs, 4,096 actor names, 250,000 faces with 2,000,000 references, and 250,000 edges with 750,000 references. Even if every independent logical maximum occurs together and every actor name occupies its 4,096-byte wire maximum, the envelope is 61,793,640 bytes (58.93 MiB), so the byte cap remains unreachable by valid state. The client validates signature, version, item, counts, UTF-8, cell arity, exact declared references, and trailing bytes before replacing selection state, then immediately releases its shared-buffer view. State beyond those bounds is `unsupported`; no partial authoritative state is published. Navigation recovery republishes the retained authoritative state through the same JSON/shared decision.

Node selections retain all accepted IDs. Their visual overlay is exact through 1,000,000 rendered matches. Above that threshold the browser deterministically takes every `ceil(matchCount / 1,000,000)`-th match in stable actor/chunk/point order and sets the diagnostics overflow flag. This bounds duplicate overlay geometry while leaving the authoritative selection and downstream controller operations exact.

## Annotation synchronization

PrePoMax sends the complete regular-callout state through WebView2 as `prepomax.annotations.updated-v1`. Each entry contains a unique name, plain text, a finite three-component absolute model-space anchor, a finite two-component display-pixel offset bounded to ±100,000, and background, border, and visibility flags. The host debounces replacement messages, limits the state to 4,096 callouts, each name to 1,024 characters, each text value to 65,536 characters, and aggregate text to 1,000,000 characters. The client repeats those checks, clones accepted state, and retains it across scene-view recreation.

The browser subtracts the scene `worldOrigin`, projects each anchor after camera renders and resize, and presents a non-interactive DOM callout above the VTK canvas. Text is assigned with `textContent`; it is never interpreted as HTML. Remove and clear operations publish replacement state.

For `Min_Annotation` and `Max_Annotation`, C# retains each result actor's authoritative extreme node ID, Float32 value, deformed Float64 coordinate, visibility, and color-contour state. It selects the global finite extrema from visible contour actors and synthesizes the same value/unit and node-ID text as legacy VTK, using the current annotation number format and background/border/visibility settings. Extrema are recomputed after actor capture, scalar/component updates, visibility or contour changes, actor rename, field-unit changes, and scene clear. They use the same bounded replacement envelope as regular callouts.

Dragging a callout emits `prepomax.annotation.moved-v1` with its name and absolute display offset. WebView2 accepts it only from the exact renderer origin, rejects unknown names and invalid/out-of-range coordinates, stores the offset in host state, and republishes the complete annotation state. Offsets are session-local, matching the legacy widget position behavior; data-derived world anchors remain unchanged.

Double-click editing is available only for non-reserved annotations. Ctrl+Enter or blur emits `prepomax.annotation.edited-v1` with a bounded non-empty text value. The host rejects edits for `Measure_Annotation`, `Min_Annotation`, and `Max_Annotation`, resolves the named annotation in the active PrePoMax view, updates `AnnotationBase.OverriddenText`, and redraws authoritative state. Escape cancels locally. The edit therefore follows normal PrePoMax annotation serialization, while the browser never owns the saved text.

In geometry-edge mode, C# accepts a validated surface-triangle pick only when two triangle vertices belong to the same PrePoMax model-edge cell. Interior visualization-triangulation edges are intentionally rejected. The closest qualifying triangle side to the validated world hit identifies the domain geometry edge; normal PrePoMax selection-history operations remain authoritative.

In point-based mixed `Geometry` mode, C# first resolves the server-derived triangle nodes back to one complete PrePoMax visualization face. It then applies the existing `FeMesh.GetGeometryIdByPrecision` precedence at the validated world hit: a geometry vertex within the threshold wins, followed by a model edge, otherwise the containing solid/shell surface. Dedicated geometry-vertex and geometry-surface modes use the same full-face reconstruction. The resulting authoritative selection returns through the existing composed geometry overlay.

## Visible-surface area resolution

The embedded client reserves Alt+left-drag for rectangle selection so ordinary left-drag orbit remains available. Left-to-right is `completelyInside: true`; right-to-left is crossing. Shift, Ctrl, and Shift+Ctrl retain add, subtract, and intersect behavior.

The hardware selector groups visible rendered-triangle indices by actor/chunk. Without a section plane, inside selection projects all three triangle vertices and keeps only triangles fully enclosed by the rectangle. With a section plane, it first clips each triangle to the retained non-negative half-space and projects every vertex of that visible polygon, so a hidden original vertex cannot reject an otherwise enclosed clipped fragment. Crossing selection keeps triangles touched by the hardware-selection rectangle, after rejecting an empty clipped polygon. `area.resolve` accepts at most 4,096 chunk entries and 100,000 primitive references, checks the current actor visibility/pickability and every primitive range, removes duplicate primitive keys, and derives actor names, source-element IDs, and triangle source-node IDs from server-owned immutable resources. When `sectionPlane` is present, the server reads its own origin-relative positions and rejects any candidate triangle wholly in the negative half-space. Success returns `validated: true` without changing the scene revision; malformed, unavailable, oversized, or out-of-range candidates return `area-invalid`.

The browser forwards only the validated result in `prepomax.area.validated-v1`. The exact-origin WebView bridge repeats the 100,000-triangle bound and validates all actor names, triangle-node triples, camera values, and operations. PrePoMax applies deduplicated node, element, part, visualization-face, geometry-vertex, geometry-edge, geometry-surface, or mixed-geometry IDs through its existing selection history, then returns the authoritative selection overlay through `prepomax.selection.updated-v1`.

Geometry-area interpretation reuses `FeMesh.GetGeometryIds`: selected surface-node sets are resolved first, then their nodes are removed before complete edges and remaining vertices are considered. Left-to-right requires the geometry entity's published surface nodes to be enclosed; right-to-left permits touched surfaces. Item-specific modes filter the resulting encoded geometry IDs by vertex, edge, or surface type. Mixed `Geometry` mode preserves all three types and publishes their node IDs, exact edge cells, and exact face-node definitions together.

This `area.resolve` path operates on the visible streamed surface and remains the fallback for v1/synthetic scenes without locator topology. In fallback crossing-node mode, nodes are the vertices of touched visible triangles rather than an independent point-frustum query. `PMXSCN2` scenes use the full-cell path below.

## Full-cell frustum resolution

For `PMXSCN2` scenes the browser first sends `frustum.resolve`, containing exactly eight finite Float64 world-space corners, the camera direction, the inside/crossing flag, and the optional absolute section plane. Corner order is the four near-plane rectangle corners (lower-left, lower-right, upper-right, upper-left), followed by the corresponding far-plane corners. The server derives and inward-orients six normalized planes; degenerate geometry or a malformed section plane returns `frustum-invalid`.

At scene replacement, each retained locator actor builds an immutable binary bounding-volume hierarchy over full-cell axis-aligned bounds. The query skips actors that are currently hidden or non-pickable, applies VTK 5.8's actor-level overall-bounds gate, and traverses only nodes whose bounds can intersect every frustum plane and, when active, the seventh retained section half-space. Point IDs use the strict six-half-space test used by `vtkExtractSelectedFrustum` 5.8, so a point exactly on a rectangle plane is not an inside point; the section boundary itself is retained inclusively to match vtk.js clipping. Cell candidates first receive bounds rejection/full-accept tests and then legacy-style edge or face polygon clipping against all active planes. Quadratic surface cells use their corner hull and `VTK_QUADRATIC_EDGE` retains the any-interpolation-point fallback. Quadratic volume cells reproduce the 5.8 extractor's observable parent-edge face-reconstruction quirk rather than substituting a geometrically corrected test. Cell IDs therefore include the same visible inside and border candidates as the legacy renderer and exclude cells wholly behind the section plane. Left-to-right whole-element selection is finalized by PrePoMax by requiring every element node in the returned visible point set. Results are deduplicated global source IDs and are independently bounded to 100,000 nodes and 100,000 elements.

Success returns `validated: true`, server-derived source node/element IDs, selected actor names, the camera direction, and the inside flag. The WebView forwards these in the exact-origin `prepomax.area.validated-v1` envelope with `locatorValidated: true`; PrePoMax then applies node, element, part, surface, geometry-vertex, geometry-edge, geometry-surface, or mixed-geometry semantics through its normal selection history. A v1/synthetic scene returns stable `frustum-unavailable`, causing the client to use the bounded visible-triangle `area.resolve` path.

The committed ten-case parity corpus is executable against the installed ActiViz 5.8 runtime with `scripts/compare-frustum-corpus-activiz.ps1`. It covers crossing edges without inside endpoints, disjoint cells with overlapping bounds, corner grazing, a cell enclosing the frustum, quadratic midpoint and volume-face behavior, plane-boundary points, and zero-length cells. The same corpus is a mandatory server test. `scripts/compare-frustum-randomized-activiz.ps1` additionally captures ActiViz results from seeded valid transformed cells and redirects the production xUnit selector to that temporary corpus; seeds 58103-58105 cover 612 cases across every supported VTK type. These checks target ActiViz/VTK 5.8 and do not guarantee parity with later VTK implementations or malformed cells.

Protocol documentation reserves two deformation modes: complete origin-relative positions, or float32 displacement vectors plus a client display scale. The WinForms bridge uses complete positions for the current frame delta. Rapid requests are coalesced and only the latest pending frame is retained.

Animation frames normally use media type `application/vnd.prepomax.animation-frame-v2`. The little-endian body starts with `PMXFRM2\0`, an Int32 actor count from 1 through 512, and a three-Float64 frame origin. Each actor then contains a length-prefixed strict UTF-8 name; positive render-point count; three origin-relative Float32 coordinates plus one Float32 scalar per render point; non-negative locator-point count; and three origin-relative Float32 coordinates per locator point. The server also accepts legacy media type `application/vnd.prepomax.animation-frame-v1` and `PMXFRM1\0` bodies with absolute Float64 coordinates. Bodies are capped at 256 MiB, 5,000,000 render points, and 5,000,000 locator points. Names must be unique; origins and coordinates must be finite; scalars may be NaN but not infinity; exact actor/render/locator counts must match the current single-chunk host scene.

The declared bound is enforced before reading, then both versions are decoded incrementally through a 64 KiB `ArrayPool<byte>` scratch buffer instead of materializing a second copy of the complete body. Fragmented network reads are accumulated; missing or trailing bytes retain stable `host-frame-format-invalid` rejection. The scratch buffer is returned on success, validation failure, cancellation, or transport failure.

Successful validation retains V2 render and locator coordinates in their origin-relative Float32 representation. Locator values remain compact in final selection state and the spatial index reconstructs world coordinates only while evaluating/refitting bounds; legacy V1 values remain absolute Float64. Immutable position and scalar resources retain the validated frame arrays and generate little-endian output directly into pooled hash and HTTP buffers, rather than staging separate `float[]` and `byte[]` bodies. Generated resources support arbitrary byte ranges and their descriptors contain the SHA-256 of the exact generated representation. The server updates actor/chunk/scene bounds and the field range, and advances revision atomically. Because animation topology is invariant, it retains BVH cell partitions and refits existing leaf and parent bounds arrays in place rather than sorting or allocating a replacement tree; indexed cell-point access avoids boxing an `IReadOnlyList` enumerator for every cell. PrePoMax validates every participating actor first, then captures only coordinates/scalars and reuses published render/locator topology, so actor-level conversion failure cannot publish a partial frame. `frame.updated` publishes only the new position/scalar descriptors and bounds. Connectivity, source point IDs, source element IDs, actor IDs, chunk IDs, and browser pipelines remain unchanged. The client downloads all replacement resources before one activation step, adjusts camera depth/clipping from the resulting visible bounds while preserving parallel scale, waits through two animation frames, records download/apply/stable-paint timing, and reports bounded telemetry to the embedded host. `prepomax.frame.activated-v1` includes `cameraAdjusted`, which is true when valid visible bounds were applied. The host additionally records compatibility/mirror capture and write/response timing. Response headers expose server read/update/total timing/allocation plus separate validation, resource, manifest, and refit timing/allocation counters for acceptance profiling.

## Control envelopes

WebSockets carry UTF-8 JSON only. Every envelope contains protocol, message ID, optional correlation ID, scene ID/revision, type, UTC timestamp, and payload. Unknown payload properties are ignored. Bulk data never appears in an envelope.

During orderly host shutdown, the event hub emits a terminal `server.shutting-down` envelope, completes its bounded subscriber channels, and closes each live WebSocket with endpoint-unavailable status. Kestrel request cancellation is propagated to in-flight generated-resource writes.

## Host scene publication

Host routes do not accept browser session credentials. They require the process-private `X-PrePoMax-Host-Token`; current scene publication requires `Content-Type: application/vnd.prepomax.render-scene-v2` and an exact `Content-Length`. The reader temporarily accepts the v1 media type/magic for compatibility with older fixtures. The default maximum is 256 MiB and can be configured with `PREPOMAX_RENDER_HOST_UPLOAD_MAX_BYTES` from 1 MiB through 1 GiB.

The version-2 body is little-endian and starts with the eight bytes `PMXSCN2\0`, followed by an Int32 actor count. Each actor contains a length-prefixed strict UTF-8 name; ARGB Int32; four material/behavior flag bytes; Float64 ambient and diffuse; Float32 line width and point size; then Int32 render-point, render-triangle, locator-point, locator-cell, and locator-connectivity-reference counts. The fourth behavior byte is backward-compatible inverted section eligibility: zero means eligible and one explicitly opts out. Render records remain:

- point: source Int32 ID, three Float64 world coordinates, Float32 scalar;
- triangle: source Int32 element ID, three UInt32 actor-local point indices.

They are followed by server-only locator records:

- locator point: source Int32 node ID and three Float64 coordinates;
- locator cell: source Int32 element ID, VTK cell-type Int32, node-count Int32, then that many actor-local Int32 point indices.

Locator topology is copied from `vtkMaxActorData.CellLocator`, which is the same full mesh used by the legacy frustum selector. It is retained in server scene state and is deliberately absent from the browser manifest/resources, so it adds host-loopback transfer and server memory but no browser download or GPU allocation. Supported VTK types have exact node counts (vertex, line, triangle, quad, tetra, voxel, hexahedron, wedge, pyramid, and their supported quadratic variants). Scene bounds are 5,000,000 locator points, 5,000,000 locator cells, and 50,000,000 connectivity references in addition to the existing 256 MiB body cap.

The server bulk-reads only after validating the declared bound, then decodes from the bounded buffer. It rejects invalid magic, strings, counts, numeric/material values, render or locator connectivity, unsupported locator cells, declared-reference mismatches, and extra/missing bytes with stable `scene-upload-*` codes. Successful validation creates origin-relative Float32 render resources, retains full locator topology separately, atomically replaces scene state, and publishes `scene.replaced` to existing subscribers. Fixture-only field toggling is unsupported after a host replacement.

Actor visibility bodies use media type `application/vnd.prepomax.actor-visibility-v1`, the eight-byte `PMXVIZ1\0` magic, an Int32 count from 1 through 512, and repeated strict UTF-8 name plus one canonical 0/1 byte. Bodies are capped at 1 MiB; duplicate names, invalid UTF-8/flags, and trailing bytes are rejected with stable `host-visibility-*` errors. Exact-name state is capped at 4,096 entries, retained across replacement, and applied through `actor.visibility.updated` without resource changes.

Camera views are `reset`, `isometric`, `front`, `back`, `left`, `right`, `top`, or `bottom`. A valid command is retained and published as `camera.updated`; retained state is also included in `scene.replaced` so a camera command issued just before a debounced host upload is not lost. These host mutations and shutdown are serialized by the WinForms adapter.

Custom cameras use media type `application/vnd.prepomax.camera-v1` and an exact 88-byte body: `PMXCAM1\0`, three Float64 position values, three Float64 focal-point values, three Float64 view-up values, and a positive Float64 parallel scale. Non-finite values, coincident position/focal points, zero view-up, and parallel direction/up vectors are rejected. Events use `kind: "custom"`; standard events use `kind: "standard"`.

Actor presentation uses media type `application/vnd.prepomax.actor-mutation-v1`: `PMXACT1\0`, old and new length-prefixed strict UTF-8 names, then ARGB Int32. Names are limited to 1,024 bytes and the body to 4 KiB. A conflicting target name returns `host-actor-name-conflict`. Successful matches advance scene revision and publish `actor.presentation.updated` with actor ID, name, and normalized front RGBA; resources and topology remain unchanged.

Discrete actor removal uses media type `application/vnd.prepomax.actor-removal-v1`: `PMXREM1\0`, an Int32 count from 1 through 512, and that many distinct length-prefixed strict UTF-8 actor names. The body is capped at 1 MiB. A successful match removes the actor, its render resources, retained visibility, and server selection topology atomically; advances scene revision once; and publishes `actor.removed` with the matched actor IDs. Missing names are idempotent and do not advance revision. The browser disposes the matching actor, mapper, and polydata pipelines and rebuilds selection overlays without fetching a replacement snapshot.

Field metadata uses media type `application/vnd.prepomax.field-metadata-v1`: `PMXFLD1\0` followed by length-prefixed strict UTF-8 field name, component, and units. Name and component are non-empty; units may be empty; each is limited to 1,024 bytes and the body to 4 KiB. Metadata is retained and applied to the next scene replacement or scalar transaction.

Scalar updates use media type `application/vnd.prepomax.scalar-update-v1`: `PMXSCL1\0`, an Int32 actor count, then actor name, Int32 value count, and contiguous little-endian Float32 values for each actor. The body is capped at 32 MiB, 512 actors, and 5,000,000 values; NaN represents unavailable data and infinity is rejected. Actor names and point counts must match the current scene. Success creates one immutable scalar resource per affected chunk, advances affected field versions and the scene revision once, recomputes the finite global range, and publishes `field.updated`; topology resource IDs do not change.
