# VTK.js renderer MVP integration

Status: first WinForms integration slice implemented on 2026-08-06.

## Boundary and intent

`FrmMain` has more than one hundred direct calls into `vtkControl`, while the controller and several domain projects expose ActiViz-derived types. Replacing that field with an unrelated WebView control would either fail to compile or require a broad, unverified rewrite.

The MVP therefore introduces a reversible dual-render seam:

- `PREPOMAX_RENDERER=vtkjs` displays the embedded VTK.js surface in the real PrePoMax render panel.
- The renderer host is a child process owned by the WinForms control and binds an ephemeral IPv4 loopback port.
- The built client and API share one origin. WebView navigation is restricted to that exact origin.
- A random host credential authorizes graceful shutdown; it is never placed in the browser URL.
- The existing ActiViz control remains hidden as a compatibility backend so unported controller operations do not crash the application. Annotation rendering is the first retired capability group and no longer calls its legacy arrow-widget methods in VTK.js mode.
- Without the environment flag, the original renderer path is unchanged.

This is an integration MVP, not yet the production renderer replacement. Visible part and deformed-result surfaces now come from real PrePoMax `PartExchangeData`; standard/custom/derived camera state, part hide/show, actor rename/color/removal, real result metadata, scalar-only component changes, scale-factor, time-increment, and complex harmonic animation frames with position/scalar deltas, validated node/element/part/surface/geometry-edge/point-mixed-geometry picks, full-cell server-frustum and mixed-geometry area selection, authoritative selection overlays, and interactive regular plus result-extrema annotations with context actions are synchronized. An executable pathological-cell corpus now agrees with ActiViz 5.8. The first large-frame bandwidth reduction is qualified; removal of the hidden compatibility backend remains a later migration slice.

## Real-scene bridge

`FrmMain.Add3DCells` captures part actors before the legacy backend consumes them. The bridge deep-copies coordinates and stable source IDs, triangulates VTK triangle/quad/quadratic-triangle/quadratic-quad cells with the same rules as `vtkMaxActor`, and debounces snapshot publication by 250 ms. Clear operations publish an empty replacement.

Snapshots use a versioned, little-endian host-only binary envelope (`PMXSCN2`) over the existing loopback origin. In addition to render surfaces, v2 carries the existing legacy `CellLocator` full mesh for future server-side selection queries. The endpoint requires the random host credential, an exact media type, and a known content length. Both sides enforce a 256 MiB default bound; the server additionally validates actor/count limits, UTF-8, finite coordinates and material values, render and locator connectivity, exact supported VTK cell arities, and trailing bytes before atomically replacing the active scene. Locator topology stays server-only; browser sessions reload only the render manifest after `scene.replaced`.

Set `PREPOMAX_RENDER_TRACE_FILE` to an explicit file path for opt-in timestamped bridge diagnostics. Normal runs do not write a trace.

## Host controls

Part hide/show uses a second bounded binary envelope (`PMXVIZ1`) containing actor names and canonical visibility bytes. The server retains at most 4,096 name states, applies them by exact ordinal name during later scene replacements, increments the scene revision for actual changes, and publishes `actor.visibility.updated`. The client mutates existing VTK actors and performs no resource requests. After each visibility batch it applies the legacy-equivalent depth/clipping adjustment against browser-visible bounds and publishes the resulting camera snapshot; an all-hidden scene preserves the last valid camera. Discrete actor removal uses the same visible-bounds policy.

Front, back, left, right, top, bottom, isometric, and zoom-to-fit/reset commands use credentialed host routes and `camera.updated` events. The last standard view is retained across a geometry-upload race and accompanies `scene.replaced`. Host scene mutations and shutdown are serialized so a close cannot interrupt an accepted upload/control request.

Saved, pasted, and user-defined cameras use a fixed 88-byte `PMXCAM1` envelope containing Float64 position, focal point, view-up, and parallel scale. The server rejects non-finite or degenerate cameras. The client subtracts `worldOrigin` from absolute position/focal coordinates before updating the active camera.

Actor rename/color uses a bounded `PMXACT1` envelope. The capture cache is updated synchronously so a later full snapshot retains the presentation, while the server publishes `actor.presentation.updated` for immediate name and RGBA changes on existing VTK pipelines.

Normal and vertical commands retain the existing PrePoMax/ActiViz derivation rules, then forward the resulting absolute position, focal point, view-up, and parallel scale through `PMXCAM1`. This keeps the visible renderer aligned without duplicating legacy camera heuristics in JavaScript.

Discrete removal uses a bounded `PMXREM1` envelope. The capture cache forgets the names before publication, the server atomically removes matching actors plus render resources and locator topology, and the client disposes only the matching VTK.js pipelines before rebuilding selection overlays. Missing names are idempotent. The transport and browser activation are ready for the result-animation controller slice.

## Real result surfaces

`AddScalarFieldOn3DCells` now enters the same deep-copy surface bridge, preserving deformed Float64 coordinates, source IDs, and per-point Float32 values. `UpdateActorSurfaceScalarField` updates the capture cache and queues the actor for a bounded scalar-only transaction; geometry capture still schedules a full replacement. Actors whose scalar arrays contain no finite values remain solid-colored in the client; real result arrays enable scalar mapping.

The `examples/fatigue_test.frd` acceptance run produced one actor with 2,850 visualization points, 5,048 triangles, field metadata `DISP / ALL / mm`, and a finite range of 0 through 0.011121182702481747. The process smoke then drives the real `FrmMain.SetFieldData` path to `DISP / U1`, observes revision 1 → 2 and range `-0.008084929548203945` through `0.0010357999708503485`, and proves that scalar IDs change while all topology/source-ID resource IDs remain stable. Host-path browser coverage additionally proves one updated actor fetches exactly one scalar resource.

## Animation frames

`AddAnimatedScalarFieldOn3DCells` registers the authoritative `NodesAnimation`, `ExtremeNodesAnimation`, and locator-node animation arrays retained by PrePoMax. `SetAnimationFrameData` now forwards and validates the common frame count plus scale-factor, time-increment, or harmonic metadata. `SetAnimationFrame` keeps the compatibility actor/scalar state synchronized, but its bounds-based camera adjustment is suppressed when VTK.js is active before the selected frame is mirrored. All participating actors are converted before the capture cache changes, preventing a rejected actor from leaving a partial multi-actor frame. Source point/element IDs and cell definitions continue to come from the base actor, avoiding identity loss from reverse-reading rendered VTK objects. A 33 ms leading-edge timer and the existing single in-flight mutation gate coalesce rapid requests so only the latest pending frame is retained.

After the initial animation snapshot establishes topology, frame activation uses a bounded `PMXFRM2` transaction containing only render coordinates/scalars and server locator coordinates. V2 includes one Float64 frame origin and represents both coordinate sets as origin-relative Float32; the server continues to accept legacy absolute-Float64 `PMXFRM1` input. The server validates counts against the current scene, reconstructs world coordinates, generates new position/scalar resources, and refits the existing locator BVH by recomputing leaf and parent bounds without re-sorting stable cell topology. It then publishes `frame.updated`. The client downloads both resources before atomically updating existing polydata, adjusts camera depth/clipping against the new visible bounds while preserving parallel scale, publishes the retained camera, and only then reports stable activation with `cameraAdjusted=true`. Connectivity, source-ID resource references, actor/chunk IDs, VTK.js pipelines, and BVH leaf membership remain stable.

The process harness retains its animation trigger and requests every post-baseline frame sequentially. It waits for a browser-reported two-`requestAnimationFrame` stable paint before requesting the next frame and records legacy activation, VTK.js capture, host write, server read/parse, server update and allocation, browser download/hash verification, VTK-array application, and paint separately. On `bitsolo-nodal.frd`, all five post-baseline frames passed across four actors while preserving topology mappings. `PMXFRM2` reduced each host transaction from 38,900,992 to 20,296,168 bytes (47.8%). Replacing full locator-BVH rebuilds with refits reduced median server update from 1,277.9 to 295.7 ms (76.9%) and host transport completion from 1,357.8 to 382.1 ms (71.9%). Compact V2 parsing plus scene/BVH locator sharing removes another 45,667,416 allocation bytes per frame. Refitting the retained BVH nodes in place subsequently reduced median server-update allocation from 78,153,584 to 61,715,864 bytes (21.0%). Coordinate/scalar-only frame capture reuses all invariant render and locator topology, cutting median VTK.js capture from 196.3 to 22.3 ms (88.6%) and combined legacy-plus-mirror activation from 228.2 to 74.5 ms (67.3%). The frame reader now decodes directly from a reusable 64 KiB `ArrayPool` buffer instead of first copying the complete request, reducing median server-read allocation from 40,625,064 to 20,370,912 bytes/frame (49.9%). Keeping locator coordinates origin-relative Float32 through scene state and BVH refit removes the remaining Float64 expansion, reducing median server-update allocation from 61,712,664 to 34,651,248 bytes/frame (43.9%). Generated position/scalar resources serialize directly from retained frame arrays into pooled hash and HTTP buffers, reducing update allocation again to 21,124,304 bytes/frame. Subphase telemetry then identified per-cell `IReadOnlyList` enumerator boxing as essentially the entire residual; indexed BVH loops reduced median update allocation to 221,176 bytes/frame (98.95% for the slice and 99.72% below the original measurement). The qualifying run reported median validation/resources/manifest/refit allocations of 0/139,296/73,760/0 bytes. Timing remains subject to run variance, so allocation comparisons are the authoritative claims.

The supplied `rotor` job is a Coriolis complex-frequency analysis, but that procedure emits only real displacement mode blocks for this non-cyclic model. `scripts/prepare-rotor-harmonic-fixture.ps1` retains the original analysis and derives a three-frequency steady-state response from its eigenbasis using real and quadrature loads, producing the paired `DISP`/`DISPI` fields consumed by PrePoMax. The FRD reader now recognizes `1PMODE` metadata independently of the legacy `MODAL` text marker, preventing method-3 complex-frequency blocks from aborting before the paired response is read. All three post-baseline harmonic phase frames passed for the derived result.

The 1,772-byte `examples/complex-frequency-paired-mini.frd` fixture makes that reader behavior deterministic and reviewable without generating the larger rotor response. It contains one four-node tetrahedron, a `1PMODE 1` header whose `100C` record deliberately omits `MODAL`, and paired `DISP`/`DISPI` values at 125 Hz. `scripts/test-frd-complex-fixture.ps1` invokes the production `CaeResults.FrdFileReader`, asserts frequency step/mode classification and all synthesized complex displacement fields, and checks the node-1 `U1` value `3 + 4i` has magnitude 5. The harness establishes the same invariant numeric culture as the PrePoMax application host, keeping direct-reader execution deterministic across Windows locales.

## Annotation context actions

Right-clicking a browser annotation opens a bounded in-viewport menu. Normal annotations expose Reset, Settings, and Delete; the reserved Measure/Min/Max annotations expose Settings only, matching the existing WinForms context-menu policy. The browser emits `prepomax.annotation.action-v1` with a bounded name and the closed action set. The exact-origin WebView handler rejects unknown annotations, unknown actions, oversized names, and reset/delete attempts against reserved names before raising a UI event. `FrmMain` then delegates to the existing `AnnotationContainer.ResetAnnotation`, `RemoveCurrentArrowAnnotation`, or Annotations settings path, so the desktop model remains authoritative and republishes annotation state.

The context menu is clamped to the viewport, consumes primary-pointer activation before it can become a VTK pick, supports Enter/Space activation and Escape dismissal, and disappears on the next authoritative annotation update. Playwright covers all three action messages and reserved-name menu reduction. The packaged `fatigue_test.frd` process smoke additionally applies edit, reset, and delete through WebView2 and requires the controller traces plus authoritative removal of the real result-node callout.

## Adaptive large selections

The original `PMXSEL1` policy rejected more than 2,000,000 IDs even though the 64 MiB byte limit could not be reached under the other bounded counts. The accepted ID capacity is now 8,000,000. The maximum combined envelope is still only 61,793,640 bytes (58.93 MiB), including maximum actor-name, face, edge, and ID sections, so multipart reassembly is unnecessary and atomic full-state replacement is preserved. Both producer and decoder reject larger declared counts, and the browser still releases the read-only WebView2 shared buffer immediately after decoding.

Authoritative IDs remain exact through the full capacity. To bound duplicate visualization geometry, node overlays remain exact through one million rendered matches and then use a deterministic stable stride capped at one million points; diagnostics report `overflow=true` when sampling occurs. A browser regression accepts 2,000,001 IDs beyond the former limit. A packaged `fatigue_test.frd` capacity smoke exercised the real C# encoder and WebView2 path with 2,000,001 unique IDs in an 8,000,044-byte envelope, retained all IDs, displayed the matching model nodes, and shut down cleanly.

## Compatibility-backend retirement

Annotation rendering is the first capability group removed from the hidden ActiViz path. In default mode, `AddArrowWidget`, named removal, and remove-all continue to call the original control unchanged. When the VTK.js renderer is active, those same `FrmMain` methods now call only `VtkJsRendererControl`; the authoritative `AnnotationContainer` remains shared application state, while the legacy control no longer creates or retains duplicate arrow widgets. This group is independent of legacy actor/camera queries and is therefore removable without weakening unported operations.

The packaged `fatigue_test.frd -ExerciseAnnotationInteraction` run asserts explicit compatibility-bypass traces for annotation add and named removal, alongside the existing move/edit/reset/delete controller and authoritative-browser checks. The real result scene, WebView2 child ownership, and graceful shutdown all remained valid. Remove-all follows the same guarded branch and builds through the normal clear lifecycle.

Camera state is the second retired group. The browser publishes bounded `prepomax.camera.changed-v1` snapshots in world coordinates after the first stable streamed frame, every standard/custom camera application, and the end of user interaction. The exact-origin WebView handler rejects missing, non-finite, degenerate, or non-positive camera values before `FrmMain` retains cloned position, focal-point, view-up, and parallel-scale values. Saved/copy camera queries, view-plane-normal queries, and closest-up queries use that renderer-neutral state in VTK.js mode.

Standard front/back/top/bottom/left/right/isometric, zoom-to-fit, and custom/saved camera commands now skip ActiViz when VTK.js is active; default mode retains the original branches. The versioned `PMXCAM2` command adds the closed operations `fit` and `adjust` while retaining `PMXCAM1` direct-set compatibility. The server validates and retains the operation with the camera vectors, so scene replacement replays the correct bounds-dependent intent rather than a stale relative action.

Normal view now derives the closest axis from the retained view-plane normal, and vertical view derives the closest cardinal up vector; both send `fit`, which applies orientation and then fits current visible VTK.js bounds. Camera-adjusting redraws send `adjust`, reproducing the legacy 1.05-radius depth calculation, one-unit camera/focal separation, and clipping reset without changing parallel scale. Pending commands suppress redundant adjustment until their authoritative browser snapshot arrives. Before the first valid snapshot, derived commands are deferred rather than falling back to ActiViz. The packaged `fatigue_test.frd -ExerciseCameraState` run requires sequential direct-set, normal-fit, vertical-fit, and adjust acknowledgements plus explicit compatibility-bypass traces.

Box zoom is now a one-shot browser interaction. `FrmMain.StartBoxZoom` arms a versioned WebView mode instead of the hidden ActiViz interactor; a primary-button rectangle reduces the orthographic parallel scale by the limiting viewport-to-selection ratio, pans the selected world-space center to the window center, resets clipping, and publishes the resulting camera snapshot. Escape, pointer cancellation, and undersized rectangles complete the mode without applying it, and every completion clears the PrePoMax toolbar toggle through `prepomax.box-zoom.ended-v1`. Scene recreation now preserves the camera callback and parallel-projection state, closing a gap where post-load browser interactions were not retained. Playwright covers apply/cancel isolation from Alt-area selection, and the packaged `fatigue_test.frd -ExerciseBoxZoom` smoke proves a reduced retained scale with an ActiViz-bypass trace.

Actor visibility no longer mutates the hidden camera in VTK.js mode. The hidden control still receives hide/show state because unported geometry tools inspect its actor registry, but its new guarded path skips `AdjustCameraDistanceAndClipping`. The browser applies that adjustment after the authoritative `actor.visibility.updated` batch and after `actor.removed`, preserving parallel scale and reporting the new world-coordinate camera. Playwright verifies hide/show camera telemetry and zero resource refetch; the packaged `fatigue_test.frd -ExerciseVisibilityCamera` run drives the real `FrmMain.HideActors`/`ShowActors` path with captured-scene identity and requires both bypass traces and browser camera completions.

Follower camera motion is now browser-owned. A bounded `prepomax.follower-view.updated-v1` WebView message carries either one tracked source node or three source nodes defining a moving plane. VTK.js resolves those IDs against each chunk's retained `sourcePointIds`, captures world-coordinate baselines, and applies the legacy in-view-plane translation or three-point basis transform after new coordinates are installed. Animation frames report `followerAdjusted` and `cameraAdjusted` in their stable activation telemetry. For complete scene replacement, the old browser view exports its resolved baseline before destruction; the new view retains it across a potentially changed world origin, loads all referenced nodes, replays the server camera, applies the follower delta, performs one bounds adjustment, waits for stable paint, and emits `prepomax.follower-view.applied-v1`. Apply, update, remove, and animation activation no longer mutate the hidden ActiViz follower camera in VTK.js mode; default mode is unchanged.

Exploded-view preview transforms are also browser-owned. `FrmMain.PreviewExplodedView` and `RemovePreviewedExplodedView` bypass the hidden ActiViz actors in VTK.js mode and publish bounded, versioned per-part translation updates. VTK.js animates them with the legacy arctangent easing curve, recomputes visible camera depth/clipping on every step, and moves authoritative selection overlays with their source actors. Point picking tests shifted bounds and converts the visual hit back to the actor's unshifted coordinates before server validation, so source topology remains authoritative. Follower-node resolution includes the visual offset. Because different browser actor transforms cannot be represented by the single server-side frustum, rectangle selection is explicitly unavailable during a nonzero preview instead of returning misleading IDs.

These transforms are transient presentation state. Applying an exploded view still updates the authoritative `FeMesh` through the existing controller and publishes the resulting baked geometry; `scene.replaced` cancels and clears the preview so the offset is not applied twice. Browser navigation recovery republishes an outstanding preview. Animated commits carry a unique 32-hex request ID: the browser echoes it only after reaching the terminal transform, then the controller bakes the mesh and waits for `prepomax.scene.applied-v1` after the replacement snapshot's stable paint before releasing the transition guard and restoring dependent presentation. A `duration + 2 s` preview timeout and a 15 s replacement timeout preserve a correct final mesh if WebView2 cannot acknowledge.

Activation animates the unmodified scene from zero to the computed offsets and then bakes those offsets. Deactivation animates the already-baked scene from zero to the negative stored part offsets and only then restores the base mesh, eliminating the previous double-offset window. Exploded-dialog cancel-to-default/cancel-to-prior commits use the same animation-before-mutation ordering. Zero-offset stationary parts remain in the outgoing batch while only nonzero offsets are retained. The packaged one-part `fatigue_test.frd` smoke verifies the correlated fallback path; `PMX2.4.0/BENDING_NEON36.pmx` exercises the full controller lifecycle across 15 actors, 828,619 points, and 1,623,416 triangles and requires browser-acknowledged animation plus stable replacement for both activation and deactivation.

Section-plane surface clipping is now browser-owned. Create, interactive update, reset/reapply, and remove send a bounded `prepomax.section-view.updated-v1` state instead of clipping hidden ActiViz actors. The absolute model-space point is converted through the current floating origin, the normal is normalized, and one VTK.js clipping plane is shared by every streamed mapper and authoritative selection-overlay mapper. State survives navigation and full scene replacement, plane changes fetch no resources, and the browser reports the active clipped-chunk count through `prepomax.section-view.applied-v1`. Point picking remains valid because Chromium can return only a visible clipped primitive and the server still validates its immutable source triangle.

Section faces and edges are now derived by C# from the retained full-cell locator, not approximated from browser surface triangles. The authenticated transient endpoint accepts absolute plane state plus exploded actor offsets and returns a bounded little-endian `PMXSEC1` response; it does not advance scene revision or retain drag-time resources. Linear volume cells produce triangulated caps and element-border lines, shell cells produce cut lines, and supported quadratic cells follow piecewise-linear chains through their midside edge nodes. Shared intersections are deduplicated, scalar values interpolate from retained locator-node values, scalar/frame updates refresh that state, and the lighten/single-color policy is applied per parent actor. The client validates exact counts/connectivity, cancels stale requests, atomically replaces non-pickable cap pipelines, and disposes them on disable or scene recreation.

Rectangle selection remains active while clipping is enabled: the retained vtk.js section half-space is applied as a seventh server BVH/geometry plane, and the visible-triangle fallback clips candidates before projection. The packaged `fatigue_test.frd -ExerciseSectionView` smoke creates, rotates, and removes the plane through the real controller and reports one cap actor with zero skipped cells for both orientations. The 370,848-cell tube PMX repeats that acceptance with one cap actor and zero skipped cells, establishing the bounded large-model path. Types 24-27 and 29 now use the exact VTK 5.8 linear subdivisions and contour tables rather than a midside-segmented approximation; randomized and coincident multi-cell differentials cover that compatibility path.

## Build and run

From a PowerShell prompt at the repository root:

```powershell
.\scripts\build-vtkjs-mvp.ps1
.\scripts\test-frd-complex-fixture.ps1
$env:PREPOMAX_RENDERER = 'vtkjs'
.\PrePoMax\bin\x64\Release\PrePoMax.exe
```

The build script produces the Vite client, publishes the .NET renderer host under the PrePoMax output, restores the pinned WebView2 SDK package, and builds `PrePoMax.sln` for x64.

Development fallbacks locate the prototype server and client directly from the repository. Packaged layouts can override discovery with `PREPOMAX_VTKJS_SERVER_PATH` and `PREPOMAX_VTKJS_CLIENT_ROOT`.
